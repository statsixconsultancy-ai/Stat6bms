1. Executive Summary

STAT6 currently offers its AI assistant as one screen among fourteen modules. This document sets out how to turn it into a platform-wide agentic framework. The assistant should be available on every screen, understand ordinary written requests, and complete work across the business: answering questions from live data, creating and updating records, and scheduling actions to run later under human supervision. It also has to keep the company's financial, payroll and customer information inside the company's control.

The central design decision is that the language model proposes and the platform decides. The model's job is limited to understanding the request and picking a registered tool with structured arguments that conform to a published schema (args_schema). Every proposal is then validated, permission-checked and, where required, approved by a person before the platform carries it out with the requesting user's own access rights. The model never gets direct database access and cannot do anything the user could not do in the normal interface.

Key architectural decisions
  1. One assistant, available on every screen. A docked panel in the application shell that receives the current screen's context (module, selected record identifiers, active filters) without the user having to restate it.
  2. Schema-governed tool calling. Every capability is a registered tool with an input schema, an output schema, a side-effect class, a required permission and an approval policy. Model output that fails validation is never executed.
  3. Data stays home by default. Query results go from the domain service straight to the user's screen. A model only sees the minimum context it needs, masked according to a four-tier data classification. Restricted data (payroll, bank details, personal identifiers) is never sent to an externally hosted model.
  4. Hybrid model hosting. A hosted inference API with zero data retention enabled (GroqCloud is evaluated) handles general reasoning. A self-hosted open-weight model inside the company network handles anything involving restricted data.
  5. Human authority over consequential actions. Payments, outbound client communication, payroll, purchase orders and bulk changes need explicit approval from an authorised role. Every step is recorded in a tamper-evident audit trail.

A review of the current code base (Section 3) shows that today's assistant is a keyword-matching prototype. Its answers come from fixed text, scheduled tasks are created with hard-coded payloads, and authentication falls back to an administrator identity when no token is supplied. These items have to be fixed before any language model is connected, and they form Phase 0 of the roadmap in Section 12.

2. Scope, Objectives and Requirements

2.1 Business objectives

  • Let any employee get work done across STAT6 by typing a plain request, without knowing which screen or form to use.
  • Give the founder and leadership accurate, permission-checked answers about company finances, people and operations on demand.
  • Let users delegate time-based work ("send the reminder tomorrow at 10 AM if the invoice is still unpaid") that runs at the right time, re-checks conditions before acting, and asks for approval when the action carries risk.
  • Keep proprietary and personal data within the company's control, in line with contractual and regulatory obligations.

2.3 Non-functional requirements

AreaRequirement
PrivacyRestricted (Tier 3) data is never sent to an externally hosted model. Hosted providers are used only with zero data retention enabled and a signed Data Processing Addendum.
AuthorisationThe assistant acts with the requesting user's identity and permissions. Permission checks are enforced in the domain services, not only in prompts or in the user interface.
IntegrityEvery figure presented to the user traces back to a tool result. Mutations are idempotent and use optimistic concurrency.
AuditabilityEvery request, tool call, approval decision and execution result is recorded in an append-only, hash-chained audit log.

AvailabilityIf the model provider is unavailable, the assistant degrades gracefully (fallback model or a clear message). Core modules stay fully usable.
Multi-tenancyConversation history, memory, tasks and audit records are isolated per organisation and per user.

2.4 Out of scope for this plan

  • Voice input, mobile applications and e-mail or chat-app channels. The architecture allows for these later.
  • Fully autonomous agents that set their own goals. Every agent action traces back to a user request or a user-approved schedule.
  • Fine-tuning or training models on company data.

4. Target Architecture

4.1 Design principles

PrincipleMeaning in practice
The model proposes, the platform decidesThe model outputs a tool name and structured arguments. Validation, authorisation, approval and execution are deterministic platform code.
Least privilegeThe agent gets the user's permissions, never more. The tool catalogue offered to the model is filtered to what the user is allowed to do.
Data minimisationEach model call gets the smallest context that answers the request. Raw records go to the screen, not to the model.
No guessingIdentifiers are resolved by lookup tools, not invented. Missing required arguments lead to a question to the user.
Defence in depthPermissions are enforced in the user interface, the orchestrator and the domain service. A failure in one layer does not grant access.
Everything is attributableEach change records who asked, what the model proposed, who approved it and what happened.

5. Platform-Wide Copilot Experience

5.1 Placement and interaction modes

  • Launcher: a fixed button in the lower-right corner of every authenticated screen, plus a keyboard shortcut (proposed Ctrl + /, which avoids the existing Ctrl + K search).
  • Side panel (default): a resizable panel docked on the right. The module underneath stays usable, so the user can check results against the screen.
  • Expanded view: a full-width workspace for long analyses, conversation history, the user's scheduled tasks and the approval queue.
  • The panel is part of the application shell, not a module tab, so the conversation and in-flight requests survive navigation between modules.

5.2 Page context envelope

Each message carries a small context envelope from the current screen. It contains identifiers and view state only, never record contents. The orchestrator fetches whatever data it needs through permission-checked tools.

{
  "module": "finance.invoices",
  "route": "/finance/invoices",
  "selected_ids": ["inv_8f21c0"],          // records the user has selected or opened
  "filters": {"status": "OVERDUE"},        // active list filters
  "locale": "en-IN",
  "timezone": "Asia/Kolkata",              // used to resolve "tomorrow at 10 AM"
  "client_time": "2026-10-09T17:40:00+05:30"
}

6. Agent Orchestration Pipeline

6.1 Request lifecycle

StepStageProcessing
1AuthenticateGateway verifies the JWT and forwards signed identity: user, organisation, role and permission set.
2Load sessionOrchestrator loads the user's conversation state (recent turns, pending clarifications, last referenced entities).
3Build tool catalogueSelect tools that are (a) relevant to the current module and request and (b) permitted for the user's role. Keep the offered set small (target: 15 tools or fewer per call) to improve selection accuracy.
4Classify and minimise contextPrivacy gateway assigns a data tier to the prompt context and pseudonymises personal and commercial identifiers.
5PlanThe routed model returns either a direct reply, a clarification question, or one or more tool calls with JSON arguments, using the provider's structured tool-calling interface.
6ValidateArguments are parsed against the tool's args_schema, then checked against business rules (entity exists and belongs to the tenant, date is in the future, amount within limits). Failures go back to the model for at most two repair attempts, otherwise the assistant asks the user.
7AuthorisePolicy engine re-checks permission and decides: execute, confirm with the user, or route for approval.
8ExecuteTool executor calls the domain service with the user's signed identity and an idempotency key. Output is validated against the tool's output_schema.
9RespondStructured results go to the client for direct rendering. If narration is needed, the model gets only aggregates or masked fields allowed by the data tier.
10AuditRequest hash, tools proposed, validated arguments, policy decision, execution result and latency are written to the audit log.

6.2 Single orchestrator with domain toolsets

A single orchestrating agent with context-dependent toolsets is recommended over a network of independent agents. The orchestrator always has cross-module tools (search, scheduling, navigation) and adds the current module's tools. This keeps one point of policy enforcement and one audit stream, and avoids agents passing data between each other outside the permission model. Domain sub-agents can be added later behind the same tool interface if a module's tool count outgrows a single catalogue.

6.3 Conversation state and memory

  • Short-term: the last N turns plus a structured record of entities referenced in the session (for example "the invoice" resolves to inv_8f21c0).
  • Long-term (optional, later phase): user preferences only (default time zone, preferred report format). Business data is never stored in memory. It is always re-fetched with current permissions.
  • Sessions are scoped by org_id and user_id, encrypted at rest, and kept for a configurable period (proposed 90 days).

6.4 Failure handling

ConditionBehaviour
Model provider timeout or errorRetry once, then fall back to the alternate model tier if the data tier allows it. Otherwise tell the user the assistant is temporarily unavailable.
Validation fails after repairsAsk the user for the specific missing or invalid field. Do not execute.
Domain service rejects the callShow the service's reason (for example "insufficient permission", "invoice already paid"). Never retry a rejected write automatically.
Partial completion of a multi-step planReport exactly which steps succeeded and which did not. Writes are not rolled back silently.

7. Tool Contracts: args_schema, Output Schemas and Validation

7.1 Tool definition standard

Every capability the assistant can use is declared once in the tool registry using the fields below. The registry generates the JSON Schema sent to the model, the server-side validators and the policy rules, so the three cannot drift apart.

FieldPurpose
name, descriptionStable identifier and a precise, example-backed description used by the model for selection.
args_schemaPydantic model defining argument names, types, enumerations, ranges and required fields.
output_schemaPydantic model the tool's result must satisfy before it is shown or passed on.
side_effectREAD, WRITE, SCHEDULE or EXTERNAL (sends something outside the company, such as e-mail or a payment).
permissionPermission string required, for example finance.invoice.read.
output_tierHighest data classification the output can contain (Section 8.2). Decides which model may see it.
approvalNONE, USER_CONFIRM or ROLE_APPROVAL(role, expiry).
idempotent_keyFields used to build the idempotency key, so a retried call cannot create duplicates.

7.2 Example: scheduling tool

The model never produces internal IDs from memory. It refers to entities by IDs returned from earlier lookup tools in the same turn, and the validator rejects any ID that did not come from a tool result.

class Precondition(BaseModel):
    entity_type: Literal["invoice", "deal", "product", "ticket"]
    entity_id: str                       # must come from a prior lookup result
    field: Literal["status", "stock_level", "stage", "priority"]
    operator: Literal["eq", "ne", "lt", "gt"]
    value: str | float

class ScheduleTaskArgs(BaseModel):
    title: str = Field(max_length=120)
    action: Literal["send_payment_reminder", "draft_purchase_order",
                    "create_follow_up", "generate_report"]
    action_args: dict                    # validated against the chosen action's own schema
    run_at_local: datetime               # naive local time, e.g. 2026-10-10T10:00
    timezone: str = "Asia/Kolkata"       # IANA name; defaults from page context
    precondition: Precondition | None = None

class ScheduleTaskResult(BaseModel):
    task_id: str
    run_at_utc: datetime
    run_at_display: str                  # "Sat 10 Oct 2026, 10:00 IST"
    status: Literal["PENDING", "WAITING_APPROVAL"]
    approval_required: bool
    approver_role: str | None

# Registry entry
schedule_task = Tool(
    name="schedule_task", args_schema=ScheduleTaskArgs, output_schema=ScheduleTaskResult,
    side_effect="SCHEDULE", permission="automation.task.create", output_tier=1,
    approval="USER_CONFIRM",             # escalates to ROLE_APPROVAL by action policy
    idempotent_key=["action", "action_args", "run_at_local"])

7.3 Worked example: "Remind Acme about their overdue invoice tomorrow at 10 AM"

#ActorAction
1ModelCalls find_invoices(customer_query="Acme", status="OVERDUE").
2Finance serviceReturns one match, inv_8f21c0 (INV-2024-002, 27,500.00, 4 days overdue). If there are several matches, the assistant asks which one.
3ModelCalls schedule_task with action send_payment_reminder, run_at_local = 2026-10-10T10:00, timezone Asia/Kolkata, precondition invoice status equals OVERDUE.
4ValidatorConfirms the schema, that the invoice ID came from step 2, that the time is in the future, and that the user holds automation.task.create. Converts to 04:30 UTC.
5Policy enginesend_payment_reminder is EXTERNAL, so it needs Finance Manager approval at execution time. The user sees a task card to confirm.
6Automation workerAt 04:30 UTC: re-reads the invoice. If it has been paid, the task is cancelled. If still overdue, an approval request goes to Finance Managers. On approval, the reminder is sent and the result recorded.

7.4 Validation and repair loop

  1. Structural: the provider's structured-output or tool-calling mode is used so arguments come back as JSON. The server parses them with Pydantic regardless. Provider-side enforcement is treated as helpful, not as a guarantee.
  2. Referential: every entity ID must exist, belong to the user's organisation, and have appeared in a tool result during the current request.
  3. Business rules: per-tool checks such as future time, working-hours window for outbound communication, amount ceilings and state-transition validity.
  4. Repair: validation errors go back to the model as structured messages. After two failed repairs the assistant stops and asks the user.

7.5 Time handling

  • The system prompt includes the user's current local time and IANA time zone from the page context.
  • The model returns a local wall-clock time plus time zone. The server converts to UTC with the standard time-zone database and stores UTC.
  • Every confirmation shows the time back in the user's own zone. Approvers in other zones see both.
  • Expressions the model cannot resolve with confidence ("later", "soon") trigger a clarification. No silent default is applied (fixes Finding 4).

8. Data Privacy, Confidentiality and Integrity

8.1 Threat model

8.2 Data classification and routing

The tier of a request is the highest tier of any context it would carry. Classification is declared on schema fields (for example Employee.salary is Tier 3), not inferred by a model.

8.3 "Data stays home": founder query example

Request: "Give me the complete compensation details of all employees, by department."
  1. The model sees only the request and the tool catalogue. It selects get_employee_compensation(group_by="department"). No payroll data is in the prompt.
  2. The policy engine confirms the caller holds the Founder role and hr.compensation.read.
  3. The HR service returns the rows. Because the output is Tier 3, the orchestrator sends them straight to the dock as a data table with totals computed by the service.
  4. If the founder then asks for commentary ("which department grew fastest?"), the follow-up goes to the self-hosted model only, inside the company network.
  5. The audit log records who viewed which dataset and when. It does not store the salary values themselves.

The same request from a Project Lead fails at step 2 with a plain explanation, and the HR service would refuse the call independently.

GroqCloud data handling - as stated in vendor documentation (accessed 9 October 2026)
  • Customer inputs and outputs are not used to train models.
  • By default, inputs and outputs may be retained for up to 30 days, for service reliability and abuse monitoring.
  • Zero Data Retention (ZDR) can be enabled in the console's Data Controls. With ZDR on, inputs and outputs are not retained for those purposes.
  • Some features (for example batch processing and fine-tuning) need data retention to work. These features would not be used for STAT6 workloads.
  • The documentation also covers prompt caching. Its interaction with ZDR must be confirmed during vendor review.
  • Groq states it holds a SOC 2 Type II attestation, available through its Trust Center. Obtain the current report and a signed DPA, and confirm the processing region, before go-live.

Source: console.groq.com/docs/your-data and groq.com trust materials. These statements must be confirmed contractually, not assumed.

Recommendation: use a hybrid deployment. Start with the hosted API (ZDR enabled, DPA signed) for Tier 0-2 and serve Tier 3 by direct rendering only. Add the self-hosted model in Phase 4 for Tier 3 narrative and as a fallback. The model router hides which back-end serves a request, so providers can be swapped or added without changing tools or the user experience.

8.5 Pseudonymisation

  • Before a Tier 2 context leaves the boundary, detected entities (customer names, e-mail addresses, phone numbers, invoice numbers) are replaced with stable placeholders such as CUSTOMER_1 or INVOICE_3. Detection combines schema knowledge (which fields hold which entity types) with an open-source detector such as Microsoft Presidio for free text.
  • The placeholder-to-value map lives only in the orchestrator's memory for the duration of the request. Placeholders in the model's reply are restored before display.
  • Amounts can be bucketed or scaled when the exact value is not needed for the reasoning task.

8.6 Network and secret controls

  • Model API keys live in a secret manager and are injected into the orchestrator only. Rotated quarterly and on staff changes.
  • Outbound network access from the orchestrator is allow-listed to the chosen provider endpoint(s). Domain services have no internet egress.
  • All traffic uses TLS. Service-to-service calls carry the gateway's signed identity, extended to cover role and permission version.
  • Prompts and model responses are not written to application logs. The audit log stores hashes and references instead.

8.7 Integrity controls

  • Numeric grounding: every number in a narrative reply is checked against values in that request's tool outputs, allowing for formatting and stated derivations such as totals. Ungrounded numbers are removed and the user is pointed to the data table.
  • Read-only access for read tools: read tools call read endpoints backed by read-only database roles.
  • Idempotency: each write carries a key derived from the tool's declared fields, so retries or double-clicks do not duplicate invoices, leads or reminders.
  • Optimistic concurrency: updates include the record version the user saw. A conflicting change elsewhere causes a refresh and re-confirmation, never an overwrite.
  • Execution-time re-validation: scheduled actions re-check preconditions and permissions when they run, not only when they were created.

8.8 Audit trail

RecordedNot recorded

Entries are append-only and each one includes the hash of the previous entry, so any alteration or deletion can be detected. The log lives in the compliance service and can be exported for audits.

8.9 Regulatory considerations

Employee and customer personal data processed through the assistant stays subject to the company's existing obligations. These include India's Digital Personal Data Protection Act, 2023, and, where EU residents' data is involved, the GDPR. Before production, legal counsel should confirm the lawful basis for processing, whether any cross-border transfer to a hosted provider is permitted, required notices to employees, and retention periods for conversation and audit data. This document does not constitute legal advice.

9. Identity, Role-Based Access and Per-User Behaviour

9.1 The agent acts as the user

Each assistant request runs under the identity of the person who made it. Tool calls carry that user's signed identity to the domain services, which apply the same permission checks as for the normal interface. Scheduled tasks run under the identity of the user who created them, re-validated at run time. If that user's access has been revoked in the meantime, the task is cancelled.

9.3 Enforcement layers

  1. Catalogue filtering: tools the user lacks permission for are never offered to the model, so it cannot propose them.
  2. Policy engine: re-checks permission on every proposed call before execution.
  3. Domain service: enforces permission, tenant filter, row-level scope (own accounts, own team) and field-level masking (salary hidden from non-HR roles), whatever the caller is.

  • Restrict domain-service ports so they accept traffic only from the gateway and orchestrator network.

10. Scheduling, Background Execution and Human-in-the-Loop

10.1 Task lifecycle

Figure 2. Scheduled task state machine. Solid arrows show the normal path. Dashed arrows show terminal exits.

10.2 Always-on scheduler worker

  • A dedicated worker process (separate from the API process) polls for due tasks at a short interval (proposed 15 seconds). This replaces the manual tick button (Finding 6).
  • On PostgreSQL, tasks are claimed with SELECT ... FOR UPDATE SKIP LOCKED, so several workers can run without executing the same task twice. This needs the PostgreSQL connection restored (Finding 10).
  • Each execution uses the task ID as its idempotency key. Transient failures retry with exponential back-off, up to a limit, then move the task to FAILED and notify the owner.
  • If volumes or workflow complexity grow (multi-step, long-running workflows), the worker can be replaced by a durable workflow engine such as Temporal without changing the task API.

10.3 Precondition evaluation

Preconditions are stored as a reference to a live entity and a comparison (Section 7.2). At execution time the worker calls the owning domain service for the current value. The present implementation stores an expected and an "actual" value in the task record itself, which cannot reflect later changes. That has to be replaced with a live read.

A requester can never approve their own request. Expired approvals move the task to EXPIRED and notify the requester. Approval requests appear in the approver's dock wherever they are in the platform, with optional e-mail notification.

10.5 Concurrent conversation and background work

Scheduling only records the task and returns at once, so the user can keep asking questions while tasks wait for their time. When a task changes state, the automation service publishes an event. The orchestrator forwards it to the owner's open sessions (server-sent events or WebSocket) and stores it for display at next login.

11.2 Evaluation suite

  • Golden set: at least 50 realistic requests per module, each with the expected tool sequence and arguments, run automatically on every prompt, model or tool change. The release gate is a pass rate agreed per module.
  • Security tests: prompt-injection payloads in record text, cross-tenant references, role-escalation attempts, attempts to retrieve Tier 3 data through a hosted route.
  • Time tests: relative and absolute expressions across time zones, daylight-saving boundaries for non-Indian users, past-time rejection.
  • Scheduler tests: concurrent workers, crash during execution, precondition flips between creation and run time, approval expiry.
